# FLOW Milestone 2 Phase 2.2 — Wallet Activation Invariants & Provider Error Isolation

**Status:** Complete (Activation Invariants & Provider Error Isolation Hardened) · Live OutLayer Provisioning Disabled (`FLOW_EXECUTION=disabled`)

---

## 1. Scope & Remediation Summary

Milestone 2 Phase 2.2 closes the two authorization and security gaps identified during the Phase 2.1 review:

1. **Precise Lifecycle Semantics (`SETUP_PENDING` → `PROVISIONING` → `ACTIVE` vs. `fundsReady`):**
   - `SETUP_PENDING` (wallet) / `REGISTERED` (job): OutLayer registration completed; `provider_wallet_id` and AES-256-GCM encrypted bearer credential durably saved in `flow.wallets` with `policy_state = 'none'` and `controller_account_id = NULL`.
   - `PROVISIONING` (wallet) / `PROVISIONED` (job): All required launch chain addresses (`near`, `base`, `solana`) and baseline capabilities (`canDeriveAddress = true`, `canReceive = false`, `canSignTransfer = false`) validated and persisted.
   - `ACTIVE` (wallet) / `ACTIVE` (job): **Custodial Provisioning & Policy Verification Complete.** Requires all 3 launch chain addresses (`near`, `base`, `solana`) and capabilities in PostgreSQL plus verified provider-backed custody policy evidence (`wallet_id === wallet.provider_wallet_id`, `policy === "stored"`, `frozen === false`, valid NEAR `controller_account_id`, non-null `rules`).
   - **Separation from Fund-Readiness:** `ACTIVE` means custodial provisioning and policy verification are complete; it does **not** mean the wallet is authorized to move or receive live customer funds. Live fund-readiness is independently evaluated by `evaluateWalletFundReadiness()` and projected as `fundsReady: false`, `canReceiveFunds: false`, `canSignTransfers: false` on `PublicWalletProjection` while `FLOW_EXECUTION=disabled`.

2. **Cross-Account Activation & Unrelated Job Protection (`WALLET_ACCOUNT_MISMATCH`):**
   - `persistRegisteredWallet`, `attachWalletAddressesAndCapabilities`, `activateWalletIfReady`, and `commitJobSuccess` lock both the provisioning job (`FOR UPDATE`) and target wallet row (`FOR UPDATE`) inside `db.$transaction` and enforce `wallet.account_id === job.account_id`.
   - Attempting to attach addresses or activate Account B's wallet using a valid leased job belonging to Account A is deterministically rejected with `FlowError("WALLET_ACCOUNT_MISMATCH")`.

3. **Elimination of Caller-Supplied String Policy Promotion (`POLICY_VERIFICATION_FAILED`):**
   - `persistRegisteredWallet` no longer accepts `policyState`; registered wallets always start at `policy_state = 'none'`.
   - `activateWalletIfReady` and `commitJobSuccess` require structured provider policy evidence (`ProviderPolicyEvidenceInput`) validated by `verifyCustodyPolicyEvidence(evidence, expectedProviderWalletId)`. Raw strings (e.g., `"stored"`), mismatched `wallet_id`s, `frozen !== false`, `policy !== "stored"`, missing/invalid NEAR `controller` accounts, or missing `rules` objects are rejected.
   - `can_receive` is held `false` during Stage 2 (`attachWalletAddressesAndCapabilities`) and only promoted to `true` after `verifyCustodyPolicyEvidence` succeeds during Stage 3 (`activateWalletIfReady`), while `can_sign_transfer` remains strictly `false`.

4. **Unconditional `FLOW_EXECUTION=disabled` Enforcement:**
   - `isFinancialExecutionDisabled()`, `evaluatePolicyReadiness()`, and `evaluateWalletFundReadiness()` inspect `process.env.FLOW_EXECUTION` directly in addition to caller parameters. Whenever `FLOW_EXECUTION=disabled`, both evaluators unconditionally return `false` (`isReady: false, canReceiveFunds: false, canSignTransfers: false`) regardless of `walletStatus`, `policySummary`, or capability flags.
   - `OUTLAYER_CAPABILITIES` sets `canSignTransfer: false` and `canReceive: false` across all networks (`near`, `base`, `ethereum`, `solana`, `bitcoin`).

5. **Provider Error Isolation (`formatIsolatedProviderFailure`):**
   - `OutLayerAdapter` never interpolates upstream error messages, response bodies, or untrusted response fields into thrown `FlowError` instances or structured logs.
   - `recordJobAmbiguous` and `recordJobTerminalFailure` validate `failure_classification` against `ALLOWED_JOB_FAILURE_CLASSIFICATIONS` (`INVALID_FAILURE_CLASSIFICATION` on unknown codes) and persist only deterministic JSON payloads containing the allowlisted classification code, static summary, integer HTTP status (`100..599`), allowlisted endpoint/chain enum, and UUID `correlationId` (`dispatch_attempt_id`). Arbitrary upstream error strings containing bearer tokens, `Authorization` headers, `Cookie` headers, email addresses, `postgresql://` URLs, or malformed HTML are completely discarded.
