This milestone implements the database schema, durable provisioning persistence, versioned credential encryption, multi-chain capability models, and the OutLayer custody adapter for FLOW Milestone 2 Phase 2.

## 1. Architectural corrections and design guarantees

### 1.1 OutLayer registration models & recovery comparison

| Dimension                     | Anonymous Random Registration (`POST /register {}`)                                                      | Deterministic NEAR-Bound Registration (`POST /register { account_id, pubkey, ... }`)                       |
| ----------------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Enclave Identity Anchor**   | Random UUID generated by OutLayer enclave.                                                               | Bound to a verified NEAR account ID via NEP-413 signature.                                                 |
| **Credential Issuance**       | Single-use bearer key (`wk_...`), returned once upon registration.                                       | Operational key (`wk_...`) paired with NEAR account full-access key.                                       |
| **Lost Credential Recovery**  | **Unrecoverable.** If `wk_...` is lost, the wallet container is unreachable.                             | **Recoverable.** NEAR account owner signs `POST /wallet/v1/auth-sign` to rotate or reissue `wk_...`.       |
| **Ambiguous Network Outcome** | **Unsafe to auto-retry.** Re-calling `POST /register` creates an orphaned, duplicate wallet container.   | **Safer.** Re-calling with identical account credentials deterministically maps to the existing container. |
| **Prerequisites**             | Zero on-chain dependencies; instantaneous.                                                               | Requires a funded NEAR account with full-access keys before registration.                                  |
| **FLOW Implementation**       | **Used for initial personal wallets**, protected by strict quarantine to `UNKNOWN` on ambiguous outcome. | **Targeted for business accounts & treasury custody** where dedicated NEAR controller keys exist.          |

### 1.2 Zero database locks across external network requests

No database transaction or row lock is ever held across an OutLayer network request:

1. **Short Lease Transaction (< 5ms):** Atomically claims execution lease (`fencing_token = fencing_token + 1`, `status = 'LEASED'`, `lease_expires_at = CURRENT_TIMESTAMP + 30s`).
2. **External HTTP Request (I/O, no DB locks held):** Dispatches to OutLayer with strict 5-second timeout and sanitization.
3. **Short Commit / Quarantine Transaction (< 10ms):** Verifies fencing token via compare-and-set (CAS) update, persists encrypted credentials and multi-chain addresses, or quarantines ambiguous errors to `UNKNOWN`.

### 1.3 Pre-dispatch retry safety vs. post-dispatch quarantine

- **Pre-dispatch crash recovery:** If a worker crashes before network dispatch (`dispatched_at IS NULL`) and the lease expires, another worker can safely reclaim the lease (`claimJobLease`), incrementing the fencing token.
- **Post-dispatch crash safety:** Once `dispatched_at IS NOT NULL`, an expired lease will **never** be re-leased by `claimJobLease`. The crash reconciler (`reconcileCrashedJobs`) quarantines the job to `UNKNOWN` (`failure_classification = 'POST_DISPATCH_AMBIGUOUS'`), requiring operator review and preventing duplicate external wallet creation.

### 1.4 Versioned credential encryption (`aes-256-gcm`)

OutLayer bearer keys (`wk_...`) are encrypted into serialized versioned envelopes before database insertion:

- 256-bit AES key with 96-bit random IV and 128-bit authentication tag.
- Envelope structure (`version: 1`, `keyId: string`, `ciphertext`, `iv`, `tag`) supports zero-downtime key rotation.
- Plaintext bearer credentials never appear in API responses, server logs, or unencrypted database columns.

### 1.5 Multi-chain address validation & capability matrix

- **NEAR Protocol:** Enforces 64-character lowercase hex implicit accounts (32-byte ed25519 public key) and valid named accounts (`alice.near`). OutLayer broadcasts transactions internally.
- **Base / EVM:** Validates `0x` + 40-hex secp256k1 addresses. OutLayer signs transactions; the FLOW caller is responsible for network broadcasting.
- **Solana:** Validates 32–44 character Base58 addresses. OutLayer signs transactions; the FLOW caller is responsible for network broadcasting.

## 2. Additive migration & database security

### 2.1 Additive migration (`20261106040000_m2_wallets`)

- `flow.wallet_status`: Enum (`SETUP_PENDING`, `PROVISIONING`, `ACTIVE`, `SETUP_FAILED`, `FROZEN`, `RECOVERY_PENDING`).
- `flow.wallets`: Stores provider wallet ID, NEAR account ID, encrypted credential envelope, key ID, key digest, and custody policy state. Enforces `UNIQUE (account_id)`.
- `flow.wallet_addresses`: Multi-chain addresses with `UNIQUE (wallet_id, network)`.
- `flow.wallet_capabilities`: Granular network capabilities with `UNIQUE (wallet_id, network)`.
- `flow.wallet_provisioning_jobs`: Durable job queue with `UNIQUE (account_id)`, `UNIQUE (idempotency_key)`, atomic fencing token, lease holder, lease expiry, dispatch timestamp, and failure classification.

### 2.3 Least-privilege PostgreSQL grants

The application role (`current_database() || '_app'`) is granted:

- `SELECT, INSERT, UPDATE` on `wallets`, `wallet_addresses`, `wallet_capabilities`, `wallet_provisioning_jobs`.
- **`DELETE` is strictly denied** across all four tables.
- All DDL (`DROP`, `ALTER`, `CREATE`) is strictly denied.

## 4. Milestone limits & remaining gates

1. **Financial execution disabled:** `FLOW_EXECUTION=disabled` remains strictly enforced. Wallet capabilities have `can_sign_transfer = false`.
2. **Offline OutLayer fixtures only:** No live OutLayer registration endpoints were called during testing. Live wallet provisioning requires explicit owner authorization.
3. **No automatic onboarding provisioning:** Wallet provisioning is decoupled from user registration and onboarding.
4. **Hosting deployments held:** Railway and Vercel deployments remain held until core multi-chain development concludes.
