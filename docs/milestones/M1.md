## Implemented security and tenant controls

- **Identity and recovery.** A stable Google subject and a verified authoritative Google mailbox are required for new Google registrations and links. Google-only accounts opt into email login with a fresh mailbox proof. A matching email alone cannot link a Google subject or enroll an email login. A Google subject binding survives unlinking. A stale mailbox reported for a linked subject pauses email login and mailbox-dependent operations. Recovery uses an enrolled method and revokes other sessions. [Identity policy](../../src/server/auth/provider.ts#L111) · [Proof consumption](../../src/server/auth/flows.ts#L279)
- **Sessions and HTTP.** Sessions use signed opaque cookies and a PostgreSQL lookup on protected requests. HTTPS cookies use `__Host-`, `HttpOnly`, `Secure`, `SameSite=Lax` and `Path=/`. The inactivity window is 12 hours, renewed on user-driven account navigation via `/api/me` where eligible. The server enforces a seven-day absolute cap. Sign-out deletes the server session, and linking or changing login methods revokes sessions. Mutations require canonical host, exact origin and JSON. OAuth uses a separate callback with browser-bound state and nonce. [Session handling](../../src/server/auth/session.ts#L47) · [HTTP validation](../../src/server/http.ts#L54)
- **Tokens and abuse.** OTPs are keyed hashes in verification storage. Auth intents bind the browser and action, expire, and cap guesses at five. Login and authenticated security code requests have separate cooldown and recipient buckets. SQL atomically updates rate counters. Session bodies expose safe session IDs. Provider access, refresh and ID tokens are discarded and the database rejects identity rows containing them. The tests scan HTTP bodies, unrelated headers and app logs for the fixture's tokens, OTPs, OAuth codes, mail and database credentials, and invite capabilities. A separate scan found no server credential names or provider fixture in the production browser assets. [Auth flows](../../src/server/auth/flows.ts) · [Rate limits](../../src/server/auth/limits.ts) · [Auth migration](../../prisma/migrations/20261106010000_m1_auth/migration.sql)
- **Ownership and business teams.** First sign-in opens automatic onboarding and creates one personal account per verified auth user in a transaction. Business creation produces a distinct account with a profile and owner membership and uses a user-scoped idempotency key. Owner, admin and member permissions come from current rows, and business mutations lock the account and recheck the actor's access inside the transaction. Invites have a 24-hour lifetime, a token digest, a verified recipient match and a check of the inviter's current authority. Acceptance and membership activation commit together. Owner transfer remains outside the M1 role policy. [Accounts](../../src/server/accounts.ts#L109) · [Teams](../../src/server/team.ts#L99) · [Invite acceptance](../../src/server/team.ts#L230)
- **M0 and financial boundaries.** Runtime, migration and bootstrap credentials remain separate. The runtime role has explicit grants and can append security events. PostgreSQL denies it schema DDL, migration history, audit reads and deletes, auth user deletion and changes to Google subject bindings. Prisma Client generation and production build require no database or authentication credentials. Financial execution remains disabled. OutLayer is the M2 custody provider, and the account ID is its handoff. The guest payer boundary remains a design for M5. Sender and recipient network and asset selection remain independent, and minimum settlement accounting and atomic reservation gates retain their original sequencing. [M0 baseline](https://github.com/OpeyemiMoses/Flow/commit/719d2dc8cdbf4014d507b9fe4bb3b82d98a8496e) · [Architecture](../architecture.md)

## Remaining limits and acceptance gate

- Live Google OAuth, verified sender delivery and deployed TLS/ingress require a staging run. The workspace had no configured live client and mail credentials. The tests exercised actual FLOW authentication routes and cookies using a signed local provider fixture.
- Deployments must preserve the canonical host, redact ingress logs and configure a trusted client IP header or an edge rate limit. Establish a retention schedule for expired auth state and security audit records. Mail delivery is best effort after commit, with a cooldown and safe resend. FLOW records no durable plaintext mail secrets for retries.
- The M1 tenant boundary relies on server authorization and tenant-scoped SQL. The service role can access the tables it has been granted. Review additional database isolation and independent authentication factors before enabling custody operations. Account reassignment after loss of all enrolled factors requires a separately reviewed recovery process.
- Review the implemented M1 scope and confirm staging evidence before closure. M2 requires explicit approval.
