# FLOW M1.3 staging preparation

**6 November 2026 · Baseline SHA: `c171793d4adb1b5b6cca9dd219e1a5d958f49260` · Staging readiness complete · Gate held pending deployment approval**

This milestone documents the staging architecture, local configuration artifacts, step-by-step setup guides, and verification plan for external testing on Render, Neon PostgreSQL 17, Google OAuth, and Resend.

## Architecture & domain evaluation

1. **Web application origin:** Render's free provider-generated HTTPS hostname (`https://<service>.onrender.com`) fully satisfies FLOW's canonical origin checks, TLS requirements, and RFC 6265bis `__Host-` cookie attributes. In Google Cloud Console's OAuth testing mode, specific subdomains are accepted without domain verification. No custom domain purchase is required for hosting.
2. **Email delivery:** Resend's free tier test domain (`onboarding@resend.dev`) restricts delivery exclusively to the account owner. Because FLOW requires testing two independent recipient mailboxes for business invitation and member workflows, Resend requires a verified sending subdomain under an existing or dedicated DNS zone ($0 incremental if using an existing zone).
3. **Infrastructure simplicity:** Native Render Node.js runtime was selected over multi-process Docker/Caddy containers to stay well within Render's 512 MB memory boundary, eliminate proxy maintenance, and minimize cold-start latency.
4. **Security boundary:** Runtime environment variables strictly prohibit `FLOW_MIGRATION_DATABASE_URL` and all DDL capabilities. Migrations are executed as an isolated operator task using `flow_staging_migrator`. `FLOW_EXECUTION=disabled` remains strictly enforced.

## Local deployment files

- `render.yaml`: Blueprint declaring the native Node service, free plan, pinned Node version (`24.22.2`), health check probe (`/api/health/live`), manual deployment gate, and `sync: false` on sensitive secrets.
- `infra/postgres/staging-bootstrap.sql`: PostgreSQL bootstrap script for Neon to establish isolated `flow_staging_migrator` and `flow_staging_app` roles.
- `.env.staging.example`: Reference template for staging configuration values.

## Step-by-step operator setup summary

1. **Neon PostgreSQL 17:** Create project, run `staging-bootstrap.sql` as project administrator, construct runtime (`flow_staging_app` with `?sslmode=verify-full`) and migration (`flow_staging_migrator` with `?sslmode=require&sslaccept=strict`) connection URLs.
2. **Google Cloud Console:** Create `flow-staging` project, configure OAuth consent screen in Testing mode with basic scopes (`openid`, `email`, `profile`), add Tester A and Tester B Gmail addresses, and create Web application OAuth client ID targeting `https://<service>.onrender.com/api/auth/callback/google`.
3. **Resend:** Add sending subdomain, configure DNS records (SPF, DKIM, MX), obtain restricted sending API key (`re_...`), and set verified `FLOW_MAIL_FROM`.
4. **Render:** Create Web Service connected to repository `OpeyemiMoses/Flow` on `main`, configure Free instance, set `/api/health/live` health path, disable auto-deploy, and enter secrets directly into the Render dashboard.
5. **Operator migration & check:** Run `npm run db:deploy`, `npm run db:status`, and `npm run db:check` via isolated operator CLI before directing user traffic.
