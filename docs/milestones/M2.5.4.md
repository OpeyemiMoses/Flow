## 1. Overview & Scope

FLOW Milestone 2 Phase 5.4 addresses source-level findings in the operator CLI and execution harness prior to authorized live testnet wallet registration. Specifically, this phase enforces strict read-only execution for `--dry-run`, decouples compatibility authorization creation from rehearsal execution, closes operator impersonation vectors by enforcing genuine authenticated session proof or verified trusted execution key comparisons, secures credential ingestion to protect shell history and process table visibility, enforces exact canonical testnet coordinator URL matching, and rejects registration attempts for accounts possessing prior wallets or provisioning jobs.

**Strict Phase Constraint:** NO live OutLayer registration, live wallet creation, fund transfers, policy promotion, or M3 tasks are executed during Phase 5.4.

## 2. Key Architectural Corrections & Technical Implementation

### 2.1 Read-Only Dry-Run Enforcement (`--dry-run`)
- In earlier revisions, `--dry-run` invoked authorization creation and touched database state.
- In M2.5.4, `scripts/rehearse-testnet-registration.ts` guarantees that `--dry-run` performs **zero database writes** and zero outbound mutation calls.
- Inspects database state via `SELECT` queries only, collects missing prerequisites safely, and outputs a diagnostic preflight report without state side effects.
- Verified by automated adversarial test snapshotting `flow.wallets`, `flow.wallet_provisioning_jobs`, `flow.provider_compatibility_authorizations`, `flow.auth_sessions`, and `flow.custody_operators` counts before and after `--dry-run` execution.

### 2.2 Decoupled Operator Authorization Action
- Removed automatic compatibility authorization creation from the rehearsal execution path (`runTestnetRehearsal`).
- Implemented `createRehearsalAuthorization` in `scripts/rehearse-testnet-registration.ts` and registered an explicit npm script (`npm run authorize:testnet`).
- Authorization MUST be created separately by an authenticated, authorized custody operator before live rehearsal can proceed.
- If live rehearsal is attempted without an existing authorization, it terminates immediately with `CUSTODY_OPERATOR_AUTHORIZATION_ERROR` without auto-creating records.

### 2.3 Privileged Operator Authentication & Impersonation Defense
- In M2.5.3, `deriveOperatorContext` permitted callers to omit session proofs, falling back to `TRUSTED_EXECUTION_CONTEXT` without verification, enabling impersonation of enrolled operators via `operatorAuthId` alone.
- In M2.5.4, `src/server/custody/job-repository.ts` enforces that every privileged custody invocation must provide either:
  1. An active, non-expired session token in `flow.auth_sessions` belonging to the specific operator (`user_id === operatorAuthId`).
  2. A verified high-entropy execution key matching `FLOW_OPERATOR_TRUSTED_EXECUTION_KEY`, validated using `timingSafeEqual` against a non-placeholder value (minimum 32 bytes).
- Supplying an operator ID without valid session proof or key immediately throws `CUSTODY_OPERATOR_AUTHENTICATION_REQUIRED`.
- Stale, expired, or other-user sessions fail closed.

### 2.4 Secure CLI Credential Handling & Audit Log Redaction
- Added support for `--session-token-file <path>` and `FLOW_CUSTODY_OPERATOR_SESSION_FILE` to read the session token securely from disk with strict whitespace trimming.
- Prevents session tokens from appearing in command-line arguments, `/proc` / process lists, or shell history.
- Enhanced log redaction in `src/foundation/logger.ts` to redact `sessionToken`, `session_token`, and execution keys from all structured log events.

### 2.5 Canonical Testnet Coordinator URL Validation
- Substring-based domain matching is strictly eliminated.
- The live rehearsal command requires exact string equality with `https://testnet-api.outlayer.ai` (`OUTLAYER_TESTNET_API_URL`).
- Loopback addresses (`127.0.0.1`, `localhost`) are rejected unless the explicit offline test mode flag is set (`FLOW_OFFLINE_TEST_MODE=1` or `offlineTestMode: true`).
- Forged domains (e.g. `https://attacker.com/testnet-api.outlayer.ai`, `https://testnet-api.outlayer.ai.attacker.com`, `http://...`) are rejected with `INVALID_CONFIGURATION`.

### 2.6 Account Validation & Invariant Protection
- Added validation requiring the target account to be a clean, unprovisioned PERSONAL account.
- Rejects accounts possessing any wallet record in `flow.wallets` regardless of status (`ACTIVE`, `PROVISIONING`, `FAILED`, etc.) with `INVALID_CONFIGURATION`.
- Rejects accounts possessing any prior job in `flow.wallet_provisioning_jobs` with `INVALID_CONFIGURATION`.
- Enforces single-registration budget: once consumed, any subsequent rehearsal fails immediately with `CUSTODY_REGISTRATION_BUDGET_EXCEEDED`.
