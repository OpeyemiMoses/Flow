# FLOW M2 Phase 2.1: Credential Persistence, Wallet Readiness, and Provider Validation Hardening

**6 November 2026 · GO for M2 Phase 2.1 review · Financial execution remains strictly disabled**

This milestone implements immediate durable credential persistence, decoupled wallet readiness, multi-chain response validation, provider error sanitization, and adversarial verification for FLOW Milestone 2 Phase 2.1.

---

## 1. Architectural remediations & design guarantees

### 1.1 Immediate durable credential persistence (two-stage protocol)

In Phase 2, `commitJobSuccess` committed credentials, derived addresses, and capabilities simultaneously at the end of provisioning. If a worker crashed _after_ receiving OutLayer's one-time bearer credential (`wk_...`) from `POST /register` but _before_ deriving all chain addresses, the bearer credential was lost forever in volatile memory, orphaning the custody container.

In Phase 2.1, persistence is decoupled into a resilient multi-stage protocol:

```
[ POST /register ] ──────────► [ persistRegisteredWallet ] ───► [ getAddress / Policy ] ───► [ activateWalletIfReady ]
 (external network)              (short atomic DB tx < 5ms)      (network I/O, no DB locks)      (short atomic DB tx < 5ms)
                                 - Inserts flow.wallets          - Correlates wallet_id          - Verifies fencing token
                                   (status: 'SETUP_PENDING')     - Validates address format      - Sets status to 'ACTIVE'
                                 - Sets job to 'REGISTERED'      - Attaches to DB                - Financial guards remain OFF
```

- **Stage 1 (`persistRegisteredWallet`):** Immediately saves `provider_wallet_id`, `encrypted_credential` (`version: 1`), `key_id`, and `key_digest` in a short atomic transaction (< 5ms). The wallet is initialized in `SETUP_PENDING` and the job transitions to `REGISTERED`. The bearer key is durably safe at rest before any further network calls.
- **Stage 2 (`attachWalletAddressesAndCapabilities`):** Derives multi-chain addresses (`near`, `base`, `solana`) and persists them idempotently (`ON CONFLICT (wallet_id, network) DO UPDATE`).
- **Stage 3 (`activateWalletIfReady`):** Verifies the atomic fencing token, checks custody policy state, and transitions the wallet to `ACTIVE` only when all criteria are met.

### 1.2 Decoupled wallet readiness & fund-receiving eligibility

A wallet having derived addresses or being marked `ACTIVE` does **not** automatically make it fund-ready. Fund readiness is modeled as an independent domain evaluation via `evaluateWalletFundReadiness`:

1. **Global Guard:** `FLOW_EXECUTION=disabled` unconditionally forces `isReady: false`, `canReceiveFunds: false`, and `canSignTransfers: false`.
2. **Status Guard:** Wallet status must be `ACTIVE` (rejects `SETUP_PENDING`, `PROVISIONING`, `SETUP_FAILED`, `FROZEN`).
3. **Custody Policy Guard:** Policy state must be verified `'stored'`, not `'none'` or `'unverified'`. Frozen wallets are immediately rejected.
4. **Multi-Chain Completeness Guard:** Verified valid addresses must exist for all three launch chains (NEAR implicit 64-hex/named, Base 0x+40-hex, Solana Base58).
5. **Signing Guard:** `can_sign_transfer` is evaluated per capability and remains `false` across all networks during M2.

### 1.3 Provider correlation & format validation

OutLayer API responses are subjected to strict validation before being processed or persisted:

- **Wallet ID Correlation:** `OutLayerAdapter.getAddress` and `getPolicy` require an `expectedWalletId` parameter. If the returned `wallet_id` does not match, the adapter throws `CUSTODY_PROVIDER_CORRELATION_ERROR`.
- **Chain Correlation:** Asserts `response.chain === requested_chain`.
- **Address Format Validation:**
  - **NEAR:** Validates 64 lowercase hexadecimal characters (32-byte ed25519 public key) for implicit accounts, or valid named account rules.
  - **Base / EVM:** Validates `^0x[0-9a-fA-F]{40}$`.
  - **Solana:** Validates Base58 encoding with 32 to 44 characters.
  - Corrupted addresses immediately throw `CUSTODY_INVALID_ADDRESS` and abort provisioning before DB writes.

### 1.4 Provider error sanitization

Arbitrary provider HTTP error bodies (such as HTML error pages, reflected bearer keys, or internal stack traces) are strictly forbidden from entering server logs or persisted database fields:

- `classifyProviderError` maps HTTP response codes and error contexts to an allowlisted classification enum (`RATE_LIMITED`, `BAD_REQUEST`, `AUTHENTICATION_FAILED`, `RESOURCE_NOT_FOUND`, `UPSTREAM_UNAVAILABLE`, `GATEWAY_TIMEOUT`, `NETWORK_ERROR`, `UNSUPPORTED_CHAIN`).
- `sanitizeErrorMessage` in `job-repository.ts` scrubs any `wk_...` bearer tokens and strips all HTML tags before writing to `flow.wallet_provisioning_jobs.last_error`.

### 1.5 Credential isolation & public projection

- Encrypted bearer credentials remain strictly isolated from API responses.
- `getAccountWalletPublicProjection` explicitly projects only public fields (`id`, `accountId`, `provider`, `providerWalletId`, `nearAccountId`, `status`, `policyState`, `handoffUrl`, `addresses`, `capabilities`).
- `encrypted_credential`, `key_id`, and `key_digest` are omitted at query time and verified absent via automated regression tests.

## 2. Review of the 5 worker crash windows

| Crash Window                                                          | State at Crash                                                                                                      | Database Guarantee                                                                                                   | Recovery Path                                                                                                                                                                                                                          |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Window 1: Immediately before dispatch**                             | Job is `LEASED`, `dispatched_at IS NULL`.                                                                           | Lease expires at `lease_expires_at`.                                                                                 | `claimJobLease` allows another worker to claim the lease, increments `fencing_token`, and retries dispatch. Safe pre-dispatch retry.                                                                                                   |
| **Window 2: During dispatch**                                         | Job is `SUBMITTED`, `dispatched_at IS NOT NULL`. Network outcome unknown.                                           | `dispatched_at` prevents `claimJobLease` from ever re-claiming the job automatically.                                | `reconcileCrashedJobs` quarantines the job to `UNKNOWN` (`POST_DISPATCH_AMBIGUOUS`). Requires operator review; blocks duplicate registration.                                                                                          |
| **Window 3: After receiving credential, before DB persistence**       | Job is `SUBMITTED`, credential held only in worker RAM. Worker crashes.                                             | DB has no wallet record; job remains `SUBMITTED`.                                                                    | `reconcileCrashedJobs` quarantines to `UNKNOWN`. Operator checks provider logs using `idempotency_key` or registers with recovered wallet ID.                                                                                          |
| **Window 4: After credential persistence, during address derivation** | Job is `REGISTERED`, `flow.wallets` has `status: 'SETUP_PENDING'` and encrypted credential at rest. Worker crashes. | Encrypted bearer credential is safe in PostgreSQL. `reconcileCrashedJobs` clears expired lease on `REGISTERED` jobs. | Recovery worker calls `claimJobLease` (succeeds with incremented fencing token), reads persisted credential from DB, and finishes address derivation **without calling OutLayer `/register` again**. Zero duplicate registration risk. |
| **Window 5: During activation**                                       | Job is `REGISTERED` or `LEASED`, addresses and capabilities persisted.                                              | Wallet remains `SETUP_PENDING`.                                                                                      | Recovery worker calls `activateWalletIfReady` with current fencing token. Atomic CAS transitions wallet and job to `ACTIVE`.                                                                                                           |
