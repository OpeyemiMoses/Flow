# FLOW M1.2 security remediation

**6 November 2026 · GO for M1.2 remediation review.** Formal M1 closure still requires live Google OAuth, verified email delivery, and HTTPS ingress verification. This work exercised a disposable PostgreSQL cluster, local provider fixtures, and the production build.

## Fixes

### M11-01 · Google unlink and concurrent callback

Better Auth resolved the Google identity before FLOW acquired the auth-user lock. Unlink could then remove the identity and all sessions before the callback acquired the lock. The callback could still issue a new session using its earlier account resolution.

The callback now records the verified Google subject and the identity row it resolved. With the same auth-user row lock used by unlink and explicit relink, it queries the active identity again immediately before session insertion. For a returning user it requires the same row ID, subject, and owner, and checks that the binding was allocated before the OAuth intent. The mailbox-drift branch performs the same check before changing email enrollment or revoking other sessions. If the callback wins the lock, unlink runs after it and deletes its new session. [OAuth callback and unlink](../../src/server/auth/flows.ts#L382) · [Locked binding check](../../src/server/auth/provider.ts#L82) · [Session hook](../../src/server/auth/provider.ts#L277)

An OAuth start is anonymous and FLOW learns the Google subject only after the token exchange. An identity row ID alone cannot detect an older request when unlink and relink have already finished by that lookup. The additive migration uses a PostgreSQL sequence with `CACHE 1` to order starts and active binding creation across app processes. This avoids relying on wall-clock ordering. Existing active bindings get order zero. Pre-upgrade OAuth intents lack an order and require a new attempt. The app role can allocate sequence values and PostgreSQL denies it `setval`. [OAuth start](../../src/server/auth/flows.ts#L319) · [Additive SQL](../../prisma/migrations/20261106030000_m12_google_binding_order/migration.sql) · [PostgreSQL sequence semantics](https://www.postgresql.org/docs/17/sql-createsequence.html)

A first-time Google registration must create its permanent subject mapping in the current transaction. That transaction may establish and use the initial binding. An ordinary callback cannot recreate a previously unlinked binding. Explicit linking still requires fresh scoped proof and the original authorized session. Same-email matching and Google recovery follow the same identity boundary. [Account creation hook](../../src/server/auth/provider.ts#L298) · [Explicit linking and session checks](../../src/server/auth/flows.ts#L419)

### M11-02 · Role change and roster read

The roster previously authorized the actor, then loaded member and invitation data in independent reads. A read that was allowed before revocation could include rows committed after revocation. The API and server-rendered team page now authorize the current session and role and fetch both result sets within one PostgreSQL `REPEATABLE READ` snapshot. A request already authorized in a pre-revocation snapshot sees only that snapshot. A new snapshot after the role change denies the former admin access to the roster. [Shared roster read](../../src/server/team.ts#L49) · [Team page](<../../src/app/(account)/accounts/[id]/team/page.tsx#L13>) · [PostgreSQL isolation semantics](https://www.postgresql.org/docs/17/transaction-iso.html)

## Review and remaining limits

- **Lock ordering.** Google session issuance and unlink serialize on the same auth-user row. The post-lock identity read uses `READ COMMITTED` so it sees any unlink that committed during the wait. A callback that loses the race rolls back the provider transaction and returns a generic failure without a session. The verification state and scoped proof remain single-use. [Transaction wrapper](../../src/foundation/prisma.ts#L28) · [Callback handling](../../src/server/auth/flows.ts#L415)
- **Roster isolation.** The read uses one DB connection and a stable snapshot without taking the business row lock used by team mutations. Query limits, response fields, invite capability handling, and server-side tenant scope remain in place. Already delivered data and pre-revocation snapshots are outside retroactive revocation. [Roster projection](../../src/server/team.ts#L41) · [Scoped account lookup](../../src/server/accounts.ts#L109)
- **Sensitive data and scope.** The new order fields stay on the server. The fixture suite still scans application logs and unintended response fields for credentials. Database credential separation, multi-chain provider contracts, and the disabled financial-execution setting were preserved. No staging release, real provider traffic, financial operation, or wallet provisioning was part of M1.2. [Leak check](../../test/support/security-server.mjs#L288) · [Execution config](../../src/foundation/environment.ts#L5) · [Provider contracts](../../src/domain/providers.ts)
- **Release limit.** A future release needs to apply the additive migration and drain any instances of the vulnerable build before accepting traffic on the remediated version. A pending OAuth attempt from before the migration must restart. The live authentication and ingress checks from M1.1 remain pending.
