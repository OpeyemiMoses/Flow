## 5. Resolution of the `FLOW_EXECUTION=disabled` Contradiction

### The Problem
Previously, FLOW's [`OutLayerAdapter`](../../src/server/custody/outlayer-adapter.ts) unconditionally threw `CUSTODY_EXECUTION_BLOCKED` whenever `FLOW_EXECUTION === "disabled"` and the endpoint was non-loopback. While this safely prevented remote network calls during development, it created an architectural deadlock: any attempt to test real provider reachability or register a test wallet would require setting `FLOW_EXECUTION=live`, which would simultaneously enable real financial execution, transaction broadcasting, and signing across the entire application.

### The Solution: Decoupled Fail-Closed Compatibility Mode
We decoupled financial execution safety from provider compatibility testing:

1. **`FLOW_EXECUTION=disabled` Remains Unconditional:**
   - Unconditionally blocks all financial transfers, signing, broadcasting, and payment completion across all networks.
   - Evaluated by `evaluateWalletFundReadiness` and `evaluateCustodyPolicyReadiness` so that no wallet can ever become funds-ready while execution is disabled.
2. **`FLOW_PROVIDER_COMPATIBILITY_MODE` Provides Scoped Testing Authorization:**
   - Values: `"disabled"` (default) or `"authorized"`.
   - When `"authorized"`, it strictly requires:
     - `FLOW_EXECUTION === "disabled"` (cannot run compatibility mode if execution is live).
     - A non-placeholder `FLOW_PROVIDER_COMPATIBILITY_TOKEN`.
     - A valid UUID `FLOW_PROVIDER_COMPATIBILITY_ACCOUNT_ID` representing an isolated developer account.
     - Destination host matching `ALLOWED_OUTLAYER_HOSTS`.
     - In-memory registration counter enforcing `FLOW_PROVIDER_COMPATIBILITY_MAX_REGISTRATIONS = 1`.
3. **Fail-Closed Behavior:**
   - Any remote call made while `FLOW_PROVIDER_COMPATIBILITY_MODE !== "authorized"` throws `CUSTODY_PROVIDER_NETWORK_ERROR: OutLayer remote calls prohibited while compatibility mode is disabled`.

## 6. Operator Recovery Authentication Hardening

In M2 Phase 4, two-person operator recovery was introduced (`escalateJobToManualReview` and `resolveQuarantinedProvisioningJob`). However, operator identities were passed as strings without database user validation.

In M2 Phase 5, we hardened operator recovery in [`src/server/custody/job-repository.ts`](../../src/server/custody/job-repository.ts):

1. **`assertOperatorIdentityRegistered(db, operatorAuthId)`:**
   - Queries `flow.auth_users` table by `id`.
   - Throws `CUSTODY_OPERATOR_AUTHORIZATION_ERROR` if the operator does not exist as a registered user.
2. **Enforced in Recovery Workflows:**
   - Added `verifyOperatorInDatabase: true` option (defaulting to enabled in production/local checks).
   - Verifies both `initiatorOperatorAuthId` and `approverOperatorAuthId` in PostgreSQL before processing escalation or resolution.
   - Enforces `initiator !== approver` (two distinct human operators).
   - Validated by new tests in [`test/database.integration.ts`](../../test/database.integration.ts).

## 7. Anonymous vs. Deterministic Wallet Registration Analysis

| Architectural Dimension | Anonymous Registration (`POST /register {}`) | Deterministic Registration (`POST /register` with NEAR Signature) |
| :--- | :--- | :--- |
| **Prerequisites** | None. Zero NEAR accounts, zero gas, zero upfront funding. | Pre-existing funded NEAR controller account with access key registered on-chain. |
| **Cost** | $0 / 0 NEAR. Free coordinator API call. | Gas fee + storage deposit on NEAR to deploy controller and store policy. |
| **Initial Policy State** | `policy: "none"` (unrestricted in OutLayer coordinator). | Can be initialized with restrictive policy via controller signature. |
| **FLOW Fund Readiness** | **BLOCKED.** FLOW's `verifyCustodyPolicyEvidence` rejects `policy: "none"`. | Eligible for activation only after on-chain policy verification passes. |
| **Credential Rotation** | Bearer `wk_...` cannot be rotated provider-side; local envelope rotation only. | Supports `PUT /wallet/v1/api-key` and stateless `Bearer near:<base64url>`. |
| **Suitability for First Live Rehearsal** | **RECOMMENDED FOR STEP 1.** Safely tests TLS, coordinator latency, response parsing, and address derivation without funding risk. | Recommended for Step 2 after NEAR controller infrastructure is funded. |

## 8. Prerequisites for Storing a Restrictive OutLayer Policy

To transition a wallet from `policy: "none"` to `policy: "stored"`:

1. **NEAR Controller Account:** A funded NEAR account (e.g., `flow-custody-controller.near` or `flow-custody.testnet`) with sufficient NEAR balance for gas and storage deposit (~0.05 NEAR per policy).
2. **Access Key Ownership:** Private key held in a secure Key Management Service (KMS) or local secure enclave.
3. **NEP-413 Transaction Signing:** Coordinator requests signed NEP-413 messages to authenticate policy updates.
4. **Coordinator Calls:**
   - `POST /wallet/v1/encrypt-policy`: Encrypts policy JSON with MPC CKD.
   - `POST /wallet/v1/sign-policy`: Coordinates MPC threshold signing for `store_wallet_policy` contract call.
5. **Contract Submission:** Controller submits `store_wallet_policy` transaction to `controller.outlayer.near`.
6. **Verification:** Coordinator verifies on-chain policy state and returns `policy: "stored"` on subsequent `GET /wallet/v1/policy` calls.
